# Технічне завдання: Task Tracker API

## 1. Вступ
Task Tracker — невеликий REST API на Flask для ведення списку завдань (створення, перегляд, оновлення, видалення). Проєкт навчальний, розробляється у межах лабораторної роботи №1.

## 2. Мета і задачі
- **Мета:** створити простий сервіс керування завданнями та відпрацювати на ньому процес розробки: ТЗ, життєвий цикл, версіонування, релізи.
- **Основні задачі:**
  - реалізувати CRUD для завдань;
  - реалізувати перевірку стану сервісу (`/health`);
  - налаштувати версіонування за SemVer і GitFlow;
  - підготувати шаблони документів для командної роботи.

## 3. Цільова аудиторія
- Студенти та невеликі команди, що ведуть особисті/командні списки завдань.
- Розробники, які інтегрують сервіс з іншими застосунками через HTTP.
- Ключові сценарії: додати завдання; переглянути список; позначити виконаним; видалити.

## 4. Функціональні вимоги
1. **Перевірка стану** — `GET /health` повертає `{"status": "ok", "version": "x.y.z"}`.
   *Приймання:* код 200, поле `version` збігається з поточною версією релізу.
2. **Створення завдання** — `POST /tasks` з полем `title`.
   *Приймання:* код 201 і об'єкт з `id`; порожній `title` → 400.
3. **Перегляд завдань** — `GET /tasks`, `GET /tasks/<id>`.
   *Приймання:* список у JSON; неіснуючий `id` → 404.
4. **Оновлення завдання** — `PUT /tasks/<id>` (`title`, `done`).
   *Приймання:* код 200, зміни збережені.
5. **Видалення завдання** — `DELETE /tasks/<id>`.
   *Приймання:* код 204; повторне видалення → 404.

## 5. Нефункціональні вимоги
- **Продуктивність:** відповідь на будь-який запит < 200 мс при до 1000 завдань.
- **Безпека:** валідація вхідних даних; у наступних версіях — авторизація через OAuth2.
- **Сумісність:** Python 3.10+; Linux/Windows/macOS; будь-який HTTP-клієнт.
- **Логування/моніторинг:** логування запитів у stdout; ендпоінт `/health`.
- **Якість:** покриття юніт-тестами не менше 80 %.

## 6. Обмеження та припущення
- Технології: Python, Flask, pytest, Git, GitHub Actions.
- Для v1.0.0 дані зберігаються в пам'яті (без БД).
- Команда 1–2 особи; тривалість проєкту ~4 тижні.
- Припущення: користувачі працюють з API через JSON.

## 7. Інтерфейс користувача (коротко)
Графічного інтерфейсу немає; взаємодія через HTTP/JSON.
Мікро-флоу: `POST /tasks` → `GET /tasks` → `PUT /tasks/1 {"done": true}` → `DELETE /tasks/1`.

## 8. Архітектурні рішення (високорівневі)
- **Сервер:** Flask-застосунок (`app.py`), модуль у пам'яті як сховище.
- **БД:** відсутня у v1.0.0; у v2.0.0 планується SQLite/PostgreSQL.
- **CI/CD:** GitHub Actions — запуск тестів на кожен push/PR; створення релізу при пуші тега `v*`.
- **Деплой:** запуск `flask run` / контейнер Docker (у планах).

## 9. План робіт та етапи
- **Ітерація 1 (спринт 1, 1 тиждень):** каркас проєкту, `/health`, CI з тестами.
- **Ітерація 2 (спринт 2, 1 тиждень):** CRUD для завдань, валідація, тести.
- **Ітерація 3 (спринт 3, 1 тиждень):** документація API, покращення логування, підготовка релізу.
- **Реліз 1 (v1.0.0):** злиття `develop` → `main`, тег `v1.0.0`, release notes.

## 10. Критерії приймання
- Усі функціональні вимоги з п. 4 виконані.
- Юніт-тести проходять (`pytest`), покриття ≥ 80 %.
- Код пройшов code review.
- Оновлено `CHANGELOG.md` та release notes.
- Створено тег `v1.0.0`.
- Тест-кейси: створення з валідним/порожнім `title`; читання існуючого/неіснуючого `id`; оновлення; подвійне видалення.
