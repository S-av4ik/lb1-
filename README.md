# Лабораторна робота №1 — Task Tracker API
Курс: Технології створення програмних продуктів.
Тема: технічне завдання, модель життєвого циклу, версіонування, шаблони.

## Структура репозиторію
| Файл | Призначення |
|------|-------------|
| `ТЗ.md` | Заповнене технічне завдання |

## Як запустити та перевірити
```bash
pip install -r requirements.txt
pytest -q            # запуск тестів
flask --app app run  # запуск сервера на :5000
curl -X POST localhost:5000/tasks -H "Content-Type: application/json" -d '{"title":"Learn Git"}'
curl localhost:5000/tasks
```
Перевірка Git-історії:
```bash
git log --oneline --graph --all
git branch -a
git tag -n
```

## Обґрунтування моделі життєвого циклу: Agile (Scrum) + GitFlow + CI/CD
Для невеликого навчального проєкту обрано **Agile/Scrum зі спринтом 1 тиждень**. Вимоги до сервісу прості, але можуть уточнюватися під час роботи (наприклад, додати авторизацію чи БД), тому гнучка ітеративна модель підходить краще за Waterfall, де зміни після затвердження вимог дорогі. Короткі спринти дають робочий інкремент щотижня, який одразу можна позначити версією за SemVer і випустити тегом.

**Переваги:** швидкий зворотний зв'язок, малі ризики на кожному кроці, природна відповідність «спринт → MINOR-версія», легко працювати в команді з 1–2 осіб. **Ризики й недоліки:** розповзання обсягу (scope creep) та слабка документація, якщо нею нехтувати; для їх зниження ТЗ і CHANGELOG ведуться як обов'язкові артефакти. Також Scrum-ритуали потрібно спрощувати під малу команду.

**Артефакти:** Product Backlog (список вимог з п. 4 ТЗ), Sprint Backlog (завдання поточного спринту), Definition of Done (`ACCEPTANCE_CHECKLIST.md`), інкремент (робоча версія в `develop`).

**Розклад:** Спринт 1 — каркас і `/health`; Спринт 2 — CRUD; Спринт 3 — документація, стабілізація, реліз v1.0.0. Планування — на початку тижня, Sprint Review — демонстрація працюючого API наприкінці, Retrospective — 15 хв після review. Гілки ведуться за спрощеним GitFlow, CI перевіряє тести на кожному пуші.
