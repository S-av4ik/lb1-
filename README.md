# Лабораторна робота №1 — Task Tracker API
Курс: Технології створення програмних продуктів.

## Що є в репозиторії
 `ТЗ.md` — технічне завдання
 `VERSIONING.md` — версії (SemVer) і гілки (GitFlow)
 `RELEASE_TEMPLATE.md` — шаблон release notes
 `CHANGELOG.md` — історія змін
 `ACCEPTANCE_CHECKLIST.md` — чекліст приймання
 `REPORT.md` — короткий звіт
 `app.py`, `test_app.py` — маленький Flask-сервіс і тести
 `.github/workflows/` — автоматичні тести і створення релізу

## Як запустити і перевірити
```bash
pip install -r requirements.txt
python -m pytest -q
python -m flask --app app run
```
Після запуску відкрити в браузері `http://127.0.0.1:5000/health`.

Подивитись історію Git:
```bash
git log --oneline --graph --all
git tag -n
```

## Чому обрано Agile (Scrum)
Для свого проєкту я обрав Agile (Scrum) зі спринтом на 1 тиждень. Проєкт невеликий, а вимоги можуть змінитися під час роботи (наприклад, потім можна додати базу даних або авторизацію). У Waterfall змінювати вимоги пізніше складно, а в Scrum кожного тижня є готовий результат, який можна перевірити і випустити як нову версію.

**Переваги:** швидко видно результат, ризики малі, зручно ставити версії за SemVer (один спринт — одна MINOR-версія), підходить для команди з 1–2 людей.

**Ризики:** вимоги можуть постійно розростатися, а документацію легко забути. Щоб цього уникнути, я веду ТЗ і CHANGELOG як обов'язкові документи і беру в спринт лише те, що можу зробити за тиждень.

**Артефакти:** Product Backlog (вимоги з пункту 4 ТЗ), Sprint Backlog (завдання на поточний тиждень), Definition of Done (`ACCEPTANCE_CHECKLIST.md`) і готовий результат у гілці `develop`.

**Розклад:** спринт 1 — каркас і `/health`; спринт 2 — робота із завданнями; спринт 3 — документація і реліз v1.0.0. На початку тижня — планування, наприкінці — демонстрація (review) і коротке обговорення, що вийшло і що покращити (retrospective). Гілки ведуться за GitFlow, а CI перевіряє тести при кожному пуші.
